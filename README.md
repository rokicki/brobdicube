# brobdicube: Solving Large Rubik's Cubes

brobdicube (named after Brobdingnag, the land of giants in *Gulliver's Travels*)
is a solver for n×n×n Rubik's Cubes that achieves O(n²/lg n) moves with a small
leading constant.  This is asymptotically faster than standard solvers, which use
Θ(n²) moves.

## Pipeline Overview

The solver is built around a two-phase pipeline:

1. **Offline: beam search** finds short master sequences of algorithms
   and stores them as `.alg` files.
2. **Online: brobdicube** loads those `.alg` files and applies them to solve any
   given cube scramble.

Both phases are described in detail below.

---

## Part 1: The Cube and Its Representation

### NxN Cube Structure

An n×n×n Rubik's Cube has three types of pieces (cubies):
- **Corners** (8 total, 3 stickers each) — solved first, in O(1) moves.
- **Wings/edges** (O(n) total, 2 stickers each) — solved next, in O(n) moves.
- **Centers** (O(n²) total, 1 sticker each) — solved last, dominating the
  total move count.

Because corners and wings contribute only lower-order terms, the algorithm
focuses almost entirely on centers.

Center cubies are grouped into **orbits** of up to 24 positions — the set of
positions reachable from one another by slice moves.  Every center cubie stays
within its orbit; the solver's job is to permute the cubies within each orbit
into their correct positions.

We index the 24 positions of an orbit in **Speffz order**: iterating through
the four quadrants of each face in the order U, L, F, R, B, D (Up, Left, Front,
Right, Back, Down), giving positions 0–23.

### The 6-Character Orbit Key

Every orbit is characterized by a **6-character key**, one character per face in
Speffz order (U L F R B D).  Each character describes that face's role:

- A **digit** (0, 1, 2, …) identifies which color group the four sticker
  positions on that face belong to.  Two faces with the same digit hold cubies
  of the same color; two faces with different digits hold cubies of different
  colors.
- The letter **`x`** means that face's positions are already fully solved and
  must not be disturbed by subsequent algorithms.

For example:
- `000000` — the trivially solved orbit (all six faces same color group).
- `010101` — faces alternate between two color groups
  (U/F/B = group 0, L/R/D = group 1).
- `000111` — first three faces (U, L, F) in group 0; last three (R, B, D) in
  group 1.
- `0x1x2x` — faces L, R, D are already solved (`x`); U, F, B are active with
  three distinct color groups.

Many keys are equivalent under the rotational symmetry of the cube; brobdicube
exploits these equivalences to reuse algorithm files across related orbit types.

An algorithm set associated with a particular key **must not move any sticker on
a face marked `x`**.  This constraint ensures that earlier reduction steps are
not undone by later ones.

### The Reduction Sequence

Center solving proceeds as a chain of **reduction steps**.  Each step is
identified by a key and uses a master sequence of algorithms that further
partitions or solves the remaining orbit colors.  A typical reduction sequence
might look like:

```
010101  →  0x1x2x  →  x0x1x2  →  solved
```

The first step (`010101`) works on all six faces simultaneously, sorting cubies
into two groups.  Subsequent steps fix some faces (`x`) and further refine the
remaining ones, until every face is solved.  Because each step's algorithms
preserve the `x` faces, the steps compose correctly.

The leading constant of the overall algorithm is L/2, where L is the total
number of algorithm stages summed across all reduction steps.  Minimizing L is the
central optimization goal of the beam search phase.

### The xorbit Representation

Internally, each orbit is represented as an `xorbit`: a 24-byte array `a[0..23]`
where `a[i]` holds the color (face index) of the cubie currently at Speffz
position `i`.  The solved state has `a[i] = i / 4` (every position holds a cubie
of its own face's color).

## Part 2: Candidate Algorithms — Source and Format

### Where Candidates Come From

The raw candidates for the beam search are center permutations: move sequences that
cyclically permute some center sticker positions in exactly one orbit and leave all other
cubies fixed.  There are millions of possible algorithms,
generated by twsearch2, but we distill them down by eliminating outer
face conjugations and only picking a single representative from
equivalence classes by symmetry and inversion.
The production pipeline reads these from `bigseed.algs`, but a short
usable prefix is `seed.algs' that has just 8-move commutators.

### The algutil Tool

`algutil` processes, expands, filters, and cost-annotates algorithm sets.  Key
flags used in the pipeline:

- `-g -U` — greedy conjugation expansion: applies the 18 face-move conjugations
  to each algorithm, deduplicating globally by symmetry class.
- `-xu` — expand each algorithm to all 48 orientation conjugations,
  deduplicating per-algorithm.
- `-f KEY` — filter to algorithms that touch only the faces indicated by non-`x`
  positions in the 6-character key.
- `-F` — filter out face-conjugate sequences: drop any algorithm whose first and
  last moves are inverse pure face moves (e.g. `U … U'`), since these cancel
  from outside and add unnecessary move count.
- `-m N` — drop algorithms whose collapsed cost exceeds N.  Applied before
  outputting, in the same pass as cost computation.
- `-c -d 1000 -pc` — cost-annotate: compute each algorithm's permutation on the
  24 orbit positions (using move depth 1000 for inner-slice cost), and emit lines
  in **costalgs format**:

  ```
  COST (cycle_notation) algorithm_text
  ```

  For example:
  ```
  2002004000 (0 9 18) U 2R U' 3L U 2R' U' 3L'
  ```

  The cost is packed with base-1000 fields: `cost = c + 1000*o + 1000000*h +
  1000000000*v`, where v = depth-3 inner moves, h = depth-2 inner moves,
  o = outer (face) moves, c = conjugation wrapper moves.  With `-d 1000`, every
  algorithm involving two depth-3 moves carries a `2 000 000 000` prefix that
  `findpermnet` strips automatically.

### Why Cost Matters

Each stage of the master sequence contributes moves in proportion to its cost
per algorithm.  Stages with `+2/+2` parallelization behavior (both row and column
directions cost only +2 moves per additional orbit) contribute the smallest
leading-constant increment.  The beam search is biased toward low-cost candidates
to keep the total leading constant small.

## Part 3: Finding Short Master Sequences

### The Combinatorial Problem

Given a pool of candidate algorithms, find a short **ordered** sequence
of them — the master sequence — such that for every possible orbit configuration,
some subsequence of the master sequence solves it.

Equivalently: the master sequence must **cover** the entire orbit state space,
where a candidate "covers" a state if applying it brings that state one step
closer to solved.  The key metric is **depth** (sequence length), with
**max_activations** (worst-case number of candidates any single orbit must apply)
and **sum_activations** (total activations across all orbit states, proportional
to average cost) as secondary objectives.

### findpermnet

`findpermnet` is the beam search program.  It reads candidate algorithms in
**costalgs format** (output of `algutil -c -d 1000 -pc`) and searches for short
master sequences that cover the full orbit state space.

`findpermnet` supports two input modes selected by the `-i` argument:

- **Permutation mode** (`-i STRING` where STRING has no `x`/`X` and length ≠ 6):
  reads raw permutations and costs; STRING is the initial multipermutation
  (e.g. `11110000`, `001122`).

- **Key mode** (`-i KEY` where KEY is exactly 6 characters of digits and/or
  `x`/`X`): reads costalgs format.  The key specifies which of the 24 orbit
  positions are active (non-`x` faces) and how many color groups there are.
  `findpermnet` remaps the full 24-slot permutations to a compact internal space
  covering only the active positions, and strips the `2 000 000 000` cost prefix
  automatically.  Examples: `010101` (all faces, 2 color groups),
  `0x1x2x` (U/F/B only, 3 color groups).

Key features:
- **Bitarray coverage tracking** with fast inverse mode once >50% is covered.
- **Suffix search** (`-x N`): backward search over missing states at the final N
  depths.
- **Cost-bucket sampling**: uniform sampling across cost buckets gives low-cost
  candidates a fair chance.
- **Template dispatch** (`-k N`): zero-overhead activation tracking enabled at
  compile time via `if constexpr`.
- Defaults to **all hardware threads** if `-t` is not specified.
- Outputs solution blocks with `initial KEY` and per-step `N: cost COST text`
  lines, which `pareto` reads directly.

### pareto

`pareto` has two modes:

**Log-file mode** (default): post-processes `findpermnet` log files to extract
and store winning algorithm sequences.  For each key (shortkey), it computes a
**Pareto front** over (depth, max_activations, sum_activations, total_cost) —
solutions that are non-dominated on all four dimensions — and writes each
Pareto-optimal solution as a `.alg` file.  `max_activations` is only used as a
Pareto dimension when both solutions being compared have it (older logs without
the field are compared on the remaining three dimensions only).

Unlike its predecessor `collect_solutions`, `pareto` reads algorithm text
directly from the `findpermnet` output (the `N: cost COST text` step lines) and
does not need to look up move sequences in a separate `.algs` file.

**Directory mode** (`-D ALGSDIR`): analyses an existing algorithm directory and
reports which `.alg` files are dominated by others, without removing anything.
Each `.alg` file is analysed under **both** planning modes independently: the
`[greedy]` entry uses stats from `.prob3-greedy` and the `[optimal]` entry from
`.prob3-optimal`.  A file is considered dominated only when **all** its entries
are dominated; cross-mode domination is allowed (an optimal entry from one file
can dominate a greedy entry from another).

The four Pareto dimensions are:

- **depth** — number of stages with *non-zero* probability (the effective
  algorithm count under each planning mode, not the nominal count in the
  filename).  Greedy planning concentrates work into fewer stages (lower
  effective depth); optimal planning spreads load across more stages.
- **max_activations** — worst-case stages needed by any single orbit state.
- **total_cost** — aggregate move cost encoded in the filename.
- **sum_prob** — sum of stage probabilities (proxy for average activations per
  orbit), read from the `.prob3` sidecar.  Compared with a tolerance of 1e-9
  to absorb floating-point summation noise.

Every `.alg` file must have at least one `.prob3-greedy` or `.prob3-optimal`
sidecar; the tool errors out if any are missing.

`-k` suppresses DOMINATED lines and prints one line per undominated entry
(filename + mode + stats), with no summary — useful for scripting.

`-u` (with `-k -D`) further deduplicates the output: entries that are identical
on all four metrics emit only one representative, so each distinct performance
point appears exactly once.

The `.alg` filename encodes the key, depth, and four cost fields (v/h/o/c):

```
{key}-{depth:04d}-{v:04d}-{h:04d}-{o:04d}-{c:04d}-{hash}.alg
```

brobdicube recognises this format (6 hyphens) alongside the older 3-field format
(5 hyphens) and the legacy packed-cost format (2 hyphens).

## Part 4: brobdicube — Solving the Cube

### Overall Solve Order

1. **Corners** — solved optimally using a precomputed pruning table (~14 moves
   worst case).
2. **Wings/edges** — solved using 3-cycles, contributing O(n) moves.
3. **Centers** — solved phase by phase using the reduction sequence; this
   dominates the total move count.

### Algorithm Loading and Planning

At startup, brobdicube reads **all** `.alg` files from the algorithm directory.
Each file represents one candidate master sequence for one step of the reduction.
There may be many candidates for each step — different sequences found by
different beam search runs, with different depths, stage probabilities, and cost
structures.

For each algorithm set, brobdicube precomputes a **probability table**: for each
possible orbit configuration, which subset of the master sequence's stages does
that orbit need?  The fraction of configurations needing each stage is the
**stage probability**, cached in `.prob3-greedy` and `.prob3-optimal` sidecar
files so subsequent runs skip recomputation.  The cache also records
`max_activations` (the largest plan size over all orbit configurations).

#### n-Dependent Algorithm Selection

The crucial insight is that the best choice of algorithm for each reduction step
**depends on n**.  For a given cube size, brobdicube uses dynamic programming to
select the globally optimal combination of algorithms across all reduction steps:

1. `bestcost(key, Mx, My)` is called recursively on the current orbit key.
2. At each step, `splitby()` identifies which color group to resolve next.
3. For **every** candidate algorithm in `algset` that handles that step's key,
   brobdicube computes its expected move cost at the given (Mx, My) using
   `avcost()` (average-case) or `wccost()` (worst-case), then adds the
   recursively computed cost of the best remaining reduction sequence.
4. The combination with the lowest total expected cost is selected.

`avcost()` and `wccost()` model the 2D parallelization structure precisely,
computing the cost of one algorithm stage as a function of strip width `w`:

- **Average cost** (`avcost`, default): For each possible number of active bits
  `bs` in a width-`w` column labeling, the probability that a column has exactly
  `bs` active rows is `p^bs * (1-p)^(w-bs)`, where `p` is the stage probability
  (fraction of orbit configurations needing this stage).  The probability that
  at least one of the Mx columns has that labeling (i.e., that the essential-
  vector cost is incurred) is `1 - (1-p^bs*(1-p)^(w-bs))^Mx`.  Summing over all
  `bs` gives the expected vertical, horizontal, and outer-turn move costs per
  strip.  A stage needed by only 1% of orbits contributes far less than one
  needed by 50%.

- **Worst-case cost** (`wccost`, enabled by `-w`): Assumes every one of the 2^w
  possible column-labeling patterns actually appears — the hardest possible
  scramble.  Vertical cost = `v * Mx` (all columns active).  Horizontal cost =
  `h * w * 2^(w-1)` (sum of Hamming weights over all 2^w patterns).  Outer-turn
  cost = `o * 2^w`.  Stage probability plays no role; every strip pays the full
  worst-case price regardless of how rarely a stage is needed.

In both cases, `optw` finds the optimal discrete strip-width allocation,
potentially mixing two adjacent widths `w` and `w+1` to exactly partition the
My rows while minimizing total cost.  A larger n supports a wider strip and
reduces the per-orbit cost; the optimal width is recomputed for every
(algorithm, n) pair.

The result is that a single algorithm library covers a wide range of n values,
with brobdicube automatically selecting the best algorithm combination and strip
width for each specific cube size at solve time — optimizing either expected
cost (for typical scrambles) or worst-case cost (for a provable upper bound).

The `-P start end` flag runs this planning sweep for sizes `start, start*2,
start*4, …` up to `end`, reporting the estimated move count at each size without
actually solving any cube.  This is useful for surveying algorithm quality across
the full range of practical cube sizes.

### Key Features

- **Parallel strip solving**: center orbits are grouped into horizontal strips.
  Multiple threads solve strips concurrently, each working on an independent
  subset of rows.  Thread count defaults to all hardware threads.
- **Lazy streaming for readmoves**: when a scramble is supplied as a move
  sequence (`-i` flag) with multiple threads, each strip's orbit rows are
  reconstructed on demand from the move sequence rather than pre-allocated.
  This eliminates the peak memory cost of holding all strips simultaneously.
- **Correct two-convention rotation**: the streaming reconstruction faithfully
  mirrors the serial path's two distinct rotation conventions —
  `std::rotate` (left-rotation) for the original moveset phase, and
  `rot4`/`rot2`/`rot4i` (right-rotation) for the corner-fix normalization
  phase — which are inverse operations and must not be conflated.

### Build

Use the Makefile:

```
make
```

### Basic Usage

```
# Solve a random 100×100×100 cube (all hardware threads):
./brobdicube -D algs3 100

# Estimate move counts across a range of sizes:
./brobdicube -P 4 100000000000000000 -D algs3

# Solve a specific scramble:
echo "2U 3R 2F 2L 3B 2D ..." | ./brobdicube -D algs3 -i 100
```

## Part 5: The Offline Pipeline

### Production pipeline: runallreductions.py

`runallreductions.py` runs the complete offline pipeline for all orbit keys,
from seed algorithms through to probability-cache precomputation.  Run it from
the `beam/` directory:

```
python3 runallreductions.py [--dir DIR] [--max-cost N]
```

**Options:**
- `--dir DIR` — working directory for all output files (default: `pipeline`,
  relative to the script).
- `--max-cost N` — drop algorithms with collapsed cost > N before running
  `findpermnet`, using `algutil -m N`.  Reduces search space for
  computationally expensive keys.

**Pipeline steps:**

1. `make` — builds all tools.
2. **Expansion** (`expanded.algs`):
   ```
   algutil -g -U < bigseed.algs | algutil -xu
   ```
3. **Per-key costalgs generation**: for each face-subset key, filters to the
   relevant face subset (if needed) and cost-annotates with
   `algutil [-m N] -c -d 1000 -pc`.
4. **findpermnet beam search**: for each reduction key, runs
   `findpermnet -b B -w W -i KEY`, where B and W are scaled inversely with
   universe size so all keys receive roughly equal CPU budget.
5. **Cleanup**: removes all `expanded*` intermediate files (which can be
   very large) now that `findpermnet` has consumed them.
6. **Pareto extraction**: runs `pareto -o algs3` on all `permnet-*.log` files.
7. **Planning sweep**: runs
   `brobdicube -P 4 100000000000000000 -D algs3`
   to estimate move counts across a wide range of cube sizes and populate
   `.prob3-greedy` / `.prob3-optimal` probability caches.

### Test pipeline: test_pipeline.py

`test_pipeline.py` exercises a small end-to-end pipeline for quick validation.
Run it from the `beam/` directory:

```
python3 test_pipeline.py
```

`seed.algs` must already exist in the current directory.  The test uses small
beam widths (b=20 to b=100) for speed and writes outputs to a `test/`
subdirectory.

### Steps

1. **Seed algorithms** (`seed.algs`): must already exist before running.

2. **Expansion** (`expanded.algs`): runs
   ```
   algutil -g -U < seed.algs | algutil -xu
   ```

3. **Cost annotation** (`expanded.costalgs`): runs
   ```
   algutil -c -d 1000 -pc < expanded.algs
   ```

4. **Face filter** (`expanded-0x0x0x.algs`): runs
   ```
   algutil -f 0x0x0x < expanded.algs
   ```
   Keeps only algorithms that touch solely the U, F, and B faces.

5. **Cost annotation of filtered set** (`expanded-0x0x0x.costalgs`).

6. **Phase 1 beam search** (`permnet-phase1.log`): runs
   ```
   findpermnet -b 20 -w 20 -i 010101 < expanded.costalgs
   ```

7. **Phase 2 beam search** (`permnet-phase2.log`): runs
   ```
   findpermnet -b 100 -w 100 -i 0x1x2x < expanded-0x0x0x.costalgs
   ```

8. **Pareto extraction** (`testalgs/`): runs
   ```
   pareto -o testalgs permnet-phase1.log permnet-phase2.log
   ```

9. **Cube solve**: runs
   ```
   brobdicube -D testalgs -p 512 65536
   ```
